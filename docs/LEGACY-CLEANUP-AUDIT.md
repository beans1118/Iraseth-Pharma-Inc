**What the dependency search established**

- [frontend/vercel.json](../frontend/vercel.json:3) builds only the employee dashboard to `dist`; [storefront-next/vercel.json](../storefront-next/vercel.json:3) selects Next.js. Neither current project calls the old storefront build or copies root admin assets.
- [Gunicorn configuration](../backend/gunicorn.conf.py:5) changes into `backend`, and [Flask application creation](../backend/app.py:32) uses Flask's normal backend-local static handling. The app does not serve repository-root `site/`, `admin.html`, `js/` or `css/`. Its explicit file-serving routes concern backups and the protected brochure source.
- Runtime/import/file-copy searches across `backend`, `frontend/src`, `storefront-next/app`, `components`, `lib`, tests and hosting configuration found no executable dependency on `legacy-storefront/` or old React `storefront/`. A comment in `storefront-next/lib/content.ts` and the content-provenance documents refer to the old source historically.
- The root README still advertises `storefront/`; `docs/GITHUB-REVIEW-CHECKLIST.md` also mentions the old build and warns against unverified cleanup. Those documents need a later documentation update when the old pipeline is formally retired. They were not silently rewritten as part of the dependency fix.
- No checked-in root `render.yaml`, `netlify.toml`, `firebase.json`, `vercel.json`, `CNAME`, `.nojekyll` or `.github` workflow was found that could settle existing external static-host routing. The new deployment plan is not evidence that an older host has already been retired.

**Cleanup risks discovered**

1. Do **not** run `npm run build` in `storefront/` as a casual verification step: its `emptyOutDir: true` can clear/rewrite the existing `site/` tree. This audit inspected the script instead of executing it.
2. Root and copied `site/admin.html` still reference `js/data.js`, which is absent at both served paths. `js/admin.js` uses `fmtPHP`, a function present in archived `legacy-storefront/data.js`. This is an existing incomplete legacy asset chain, not a regression introduced by the current apps. No restoration or repair was attempted. If maintaining the old static admin remains a requirement, review that missing dependency before retiring historical sources.
3. The old app's `HashRouter` publishes `/#/catalog`, `/#/mission` and `/#/locations`. The new app has `/products`, `/mission-vision` and `/contact`. Hash fragments are client-side; a server-only redirect does not automatically migrate those bookmarks. The `@modal/[...catchAll]` Next route only closes intercepted modals; it is not a public old-URL migration layer.
4. The old client uses localhost API settings and mock fallback behavior; it should not accidentally become the staging app because a provider selected the wrong folder. Its direct legacy-order submission also differs from the current inquiry → Pending Order → approval flow.
5. Static-generated duplicates do not prove safe deletion while external publishing is unknown. This audit did not inspect or change cloud services, DNS, external bookmarks or a production host.
6. PNG byte differences alone do not establish visual differences: the CEO copies have identical decoded pixels. No automatic deduplication, recompression or asset editing was performed by this recovery.

**Recommendation for a later authorized cleanup**

First confirm all public and employee hostnames point to the intended current apps and record the existing static-host publish roots. The three unreferenced archive files above are the repository-level removal candidates; keep `legacy-storefront/data.js` until the missing legacy `js/data.js` repair/provenance risk is resolved or the old admin is retired. Then decide whether to retire the old React build, its hash URLs and `copy-admin.mjs` together. Only after that decision should root admin scripts/styles/assets and `site/` be considered for removal. Keep the current three application roots, brochure review material and approved images. No deletion is performed by this report.
